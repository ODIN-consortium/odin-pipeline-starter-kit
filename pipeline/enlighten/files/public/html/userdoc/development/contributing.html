Contributing Guidelines¶

Welcome to OpenEnlighten! This document outlines how to contribute effectively to the project.

Getting Started¶

Prerequisites:

  1. Development Environment: Set up per Development Setup guide

  2. Git Knowledge: Basic git commands and workflows

  3. Code Standards: Familiarity with Python and TypeScript best practices

  4. Testing: Understanding of testing procedures per Testing Guide guide

First Contribution:

  1. Fork the Repository: Create your own fork on GitHub

  2. Clone Locally: Clone your fork to your development machine

  3. Create Branch: Create a feature branch for your changes

  4. Make Changes: Follow coding standards and add tests

  5. Submit PR: Submit a pull request with clear description

Contribution Types¶

Code Contributions:

  • Bug Fixes: Fix reported issues

  • Features: Implement new functionality

  • Performance: Optimize existing code

  • Documentation: Improve code documentation

Non-Code Contributions:

  • Documentation: User guides, API documentation

  • Testing: Additional test cases and scenarios

  • Issues: Report bugs and suggest features

  • Reviews: Review pull requests from other contributors

Development Workflow¶

Branch Strategy:

# Create feature branch
git checkout -b feature/your-feature-name

# Work on your changes
# ... make changes, add tests, update docs ...

# Commit with clear message
git commit -m "Add feature: brief description"

# Push to your fork
git push origin feature/your-feature-name

# Create pull request on GitHub

Commit Standards:

Use clear, descriptive commit messages:

# Format: Type: Brief description

feat: Add new colormap configuration options
fix: Resolve plugin loading timeout issue
docs: Update API documentation for client config
test: Add integration tests for plugin system
refactor: Simplify configuration loading logic
perf: Optimize data processing pipeline

Code Standards¶

Python Standards:

  • PEP 8: Follow Python style guidelines

  • Type Hints: Use type annotations for better code clarity

  • Docstrings: Document all public functions and classes

  • Error Handling: Use appropriate exception handling

def process_data(data: Dict[str, Any], config: ServerConfig) -> ProcessedData:
    """Process seismic data according to configuration.

    Args:
        data: Raw seismic data dictionary
        config: Server configuration object

    Returns:
        ProcessedData: Processed seismic data object

    Raises:
        ProcessingError: If data processing fails
        ValidationError: If data format is invalid
    """
    try:
        # Processing logic here
        return ProcessedData(data)
    except Exception as e:
        raise ProcessingError(f"Data processing failed: {e}")

TypeScript Standards:

  • Strict Mode: Use TypeScript strict mode

  • Interfaces: Define clear interfaces for data structures

  • Components: Follow Angular component best practices

  • Services: Implement proper dependency injection

interface SeismicDataPoint {
  timestamp: Date;
  amplitude: number;
  location: {
    latitude: number;
    longitude: number;
    depth: number;
  };
}

@Injectable({
  providedIn: 'root'
})
export class DataService {
  constructor(private http: HttpClient) {}

  fetchSeismicData(): Observable<SeismicDataPoint[]> {
    return this.http.get<SeismicDataPoint[]>('/api/data');
  }
}

Testing Requirements¶

All Contributions Must Include:

  • Unit Tests: Test individual functions/components

  • Integration Tests: Test component interactions (if applicable)

  • Documentation Tests: Verify documentation examples work

  • Test Coverage: Maintain or improve coverage percentage

Testing Checklist:

# Backend testing
python -m pytest tests/ -v --cov=app
python -m flake8 src/
python -m black --check src/ tests/

# Frontend testing
npm test
npm run lint
npm run build

Test Example for New Feature:

def test_new_feature():
    """Test the new feature works correctly."""
    # Arrange
    config = ServerConfig()
    input_data = {"test": "data"}

    # Act
    result = new_feature_function(input_data, config)

    # Assert
    assert result.success is True
    assert result.data is not None

Documentation Requirements¶

Code Documentation:

  • Docstrings: All public functions must have docstrings

  • Type Hints: Use comprehensive type annotations

  • Comments: Explain complex logic with inline comments

  • Examples: Include usage examples in docstrings

User Documentation:

  • API Changes: Update API documentation for any endpoint changes

  • Configuration: Document new configuration options

  • Features: Add user guide sections for new features

  • Breaking Changes: Clearly document any breaking changes

Documentation Format:

class NewConfigSection(BaseModel):
    """Configuration section for new feature.

    This class handles configuration for the new seismic processing
    feature, including filtering options and output formats.

    Attributes:
        enable_filtering: Enable/disable data filtering
        filter_frequency: Frequency threshold for filtering
        output_format: Desired output format ('json' or 'csv')

    Example:
        >>> config = NewConfigSection(
        ...     enable_filtering=True,
        ...     filter_frequency=10.0,
        ...     output_format='json'
        ... )
        >>> config.enable_filtering
        True
    """
    enable_filtering: bool = Field(
        default=True,
        description="Enable automatic data filtering"
    )
    filter_frequency: float = Field(
        default=5.0,
        gt=0,
        description="Frequency threshold in Hz"
    )
    output_format: str = Field(
        default='json',
        regex='^(json|csv)$',
        description="Output format: 'json' or 'csv'"
    )

Pull Request Process¶

Before Submitting:

  1. Self Review: Review your own changes thoroughly

  2. Test Locally: Run full test suite locally

  3. Update Documentation: Ensure docs reflect your changes

  4. Check Conflicts: Rebase if needed to resolve conflicts

PR Description Template:

## Summary
Brief description of what this PR does.

## Changes
- List of main changes
- Another change
- Third change

## Testing
- [ ] Unit tests pass
- [ ] Integration tests pass
- [ ] Manual testing completed
- [ ] Documentation updated

## Breaking Changes
List any breaking changes (if applicable)

## Related Issues
Closes #123
Related to #456

Review Process:

  1. Automated Checks: CI/CD pipeline runs tests and checks

  2. Code Review: Maintainers review code quality and design

  3. Testing Review: Verify test coverage and quality

  4. Documentation Review: Check documentation accuracy and completeness

Code Review Guidelines¶

For Contributors:

  • Be Responsive: Respond to review comments promptly

  • Be Open: Accept feedback constructively

  • Explain Decisions: Justify design choices when asked

  • Update Promptly: Make requested changes efficiently

For Reviewers:

  • Be Constructive: Provide actionable feedback

  • Be Specific: Point to exact lines and suggest improvements

  • Be Respectful: Maintain professional and helpful tone

  • Be Thorough: Check code quality, tests, and documentation

Common Issues¶

Frequent Problems:

  1. Missing Tests: Always include tests for new functionality

  2. Code Style: Run formatters and linters before committing

  3. Documentation: Keep documentation in sync with code changes

  4. Breaking Changes: Minimize and clearly document breaking changes

Getting Help:

  • Issues: Create GitHub issues for questions or bugs

  • Discussions: Use GitHub discussions for design questions

  • Documentation: Check existing documentation first

  • Community: Engage respectfully with other contributors

Issue Reporting:

## Bug Report Template

**Description**: Clear description of the issue

**Steps to Reproduce**:
1. First step
2. Second step
3. Third step

**Expected Behavior**: What should happen

**Actual Behavior**: What actually happens

**Environment**:
- OS: Windows/Linux/macOS
- Python Version: 3.12.x
- Node Version: 18.x
- Browser: Chrome/Firefox/Safari (if applicable)

**Additional Context**: Any other relevant information

Recognition¶

Contributor Recognition:

  • Contributors are listed in project documentation

  • Significant contributions are highlighted in release notes

  • Community members can become maintainers through consistent contributions

  • All contributions, no matter how small, are valued and appreciated

Maintainer Responsibilities:

  • Review pull requests promptly and constructively

  • Maintain code quality and project standards

  • Help onboard new contributors

  • Make final decisions on architectural changes

Thank you for contributing to OpenEnlighten! Your efforts help make seismic data analysis more accessible and powerful for researchers worldwide.
