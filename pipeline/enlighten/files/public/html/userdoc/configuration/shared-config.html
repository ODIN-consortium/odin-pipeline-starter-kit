Shared Configuration System¶

This guide explains the shared configuration architecture used in OpenEnlighten to centralize settings across all components.

Architecture Overview¶

OpenEnlighten uses a shared configuration folder (/config) to centralize settings across all components. This approach ensures consistency between development and production environments while simplifying configuration management.

Configuration Files¶

The shared configuration system uses two primary YAML files:

client_config.yaml¶

Purpose: Frontend configuration for Cesium and UI settings

Location: /config/client_config.yaml

Contains:

  • Cesium layer definitions (base layers, terrain)

  • Cesium viewer widget settings

  • UI configuration options

  • Client-side application settings

Example Structure:

# Cesium 3D visualization layers
cesiumLayers:
  base:
    - type: "OSM"
      name: "OpenStreetMap"
      # See: https://cesium.com/learn/cesiumjs/ref-doc/OpenStreetMapImageryProvider.html
  terrain:
    - type: "Ellipsoid"
      name: "WGS84 Ellipsoid"
      # See: https://cesium.com/learn/cesiumjs/ref-doc/EllipsoidTerrainProvider.html

# Cesium viewer widget configuration
cesiumViewer:
  homeButton: false
  baseLayerPicker: true
  geocoder: true
  fullscreenButton: true

# Additional client settings
cesiumDefaultViewRectangleDegrees: [-10, 30, 50, 70]
cesiumWMSFeatureInSeparateTab: true

server_config.yaml¶

Purpose: Backend configuration for plugins and services

Location: /config/server_config.yaml

Contains:

  • Plugin configurations and settings

  • Service endpoint definitions

  • Backend application settings

  • Database and external service connections

Example Structure:

# Plugin system configuration
plugins:
  obspy_fdsn:
    enabled: true
    config:
      base_url: "http://service.iris.edu"
      timeout: 30
      max_results: 1000

# Server settings
server:
  debug: false
  log_level: "INFO"
  cors_origins: ["http://localhost:4200"]

Configuration Loading¶

Backend (FastAPI)¶

The FastAPI backend loads configuration using command-line arguments:

Command Line Usage:

python dev_server.py --config-dir ../../config

Programmatic Loading:

from app.core.config import load_config

# Load configuration from directory
config = load_config("path/to/config")

# Access configuration values
client_config = config.client
server_config = config.server

Configuration Validation:

The backend uses Pydantic models to validate configuration structure:

from pydantic import BaseModel, validator

class ClientConfig(BaseModel):
    cesiumLayers: CesiumLayers
    cesiumViewer: dict = {}

    @validator('cesiumLayers')
    def validate_layers(cls, v):
        if not v.base:
            raise ValueError('At least one base layer required')
        return v

Frontend (Angular)¶

The Angular frontend loads configuration through the API:

Configuration Service:

@Injectable()
export class ConfigService {
  private config: ClientConfig;

  async loadConfig(): Promise<ClientConfig> {
    const response = await this.http.get('/api/config/client').toPromise();
    this.config = response as ClientConfig;
    return this.config;
  }

  getConfig(): ClientConfig {
    return this.config;
  }
}

Application Initialization:

// app.module.ts
export function configInitializer(configService: ConfigService) {
  return () => configService.loadConfig();
}

@NgModule({
  providers: [
    {
      provide: APP_INITIALIZER,
      useFactory: configInitializer,
      deps: [ConfigService],
      multi: true
    }
  ]
})

Usage in Components:

export class MapComponent implements OnInit {

  constructor(private configService: ConfigService) {}

  ngOnInit() {
    const config = this.configService.getConfig();
    this.initializeCesium(config.cesiumLayers, config.cesiumViewer);
  }
}

Benefits of Shared Configuration¶

Centralized Management¶

  • Single Source of Truth: All settings in one location

  • Version Control: Configuration changes tracked with code

  • Environment Consistency: Same config across dev/test/prod

  • Simplified Deployment: Configuration bundled with application

Validation and Safety¶

  • Schema Validation: Pydantic models ensure config correctness

  • Type Safety: Strong typing prevents configuration errors

  • Error Prevention: Invalid configurations prevent server startup

  • Clear Error Messages: Specific validation feedback

Development Benefits¶

  • Hot Reloading: Changes take effect with server restart

  • IDE Support: YAML syntax highlighting and validation

  • Documentation: Self-documenting configuration structure

  • Testing: Consistent configuration across test environments

File Structure¶

The shared configuration follows this structure:

/config/
├── client_config.yaml    # Frontend settings (Cesium, UI)
├── server_config.yaml    # Backend settings (plugins, services)
└── [future configs...]   # Additional configuration files

Naming Conventions:

  • Use snake_case for configuration keys

  • Group related settings under common prefixes

  • Use descriptive names that indicate purpose

  • Follow consistent naming patterns across files

Development Workflow¶

Making Configuration Changes¶

  1. Edit Configuration: Modify files in /config directory

  2. Validate Syntax: Check YAML syntax and structure

  3. Test Changes: Restart servers to pick up changes

  4. Verify Loading: Check API or logs for configuration validation

  5. Commit Changes: Version control configuration with code

Validation Process:

# Test configuration loading
python -c "from app.core.config import load_config; load_config('config')"

Environment-Specific Configuration¶

Development:

# config/client_config.yaml (dev)
cesiumViewer:
  baseLayerPicker: true  # Enable layer picker for testing

# Additional debug layers for development
cesiumLayers:
  base:
    - type: "OSM"
      name: "OpenStreetMap (Dev)"

Production:

# config/client_config.yaml (prod)
cesiumViewer:
  baseLayerPicker: false  # Simplified UI for end users

Configuration Validation¶

Schema Validation¶

The system validates configuration against Pydantic schemas:

Backend Validation:

# Automatic validation on server startup
try:
    config = load_config(config_dir)
except ValidationError as e:
    logger.error(f"Configuration validation failed: {e}")
    sys.exit(1)

Manual Validation:

# Validate configuration before deployment
python -m app.core.config_validator --config-dir config

Error Handling¶

Common validation errors and solutions:

YAML Syntax Errors:

Error: Invalid YAML syntax in client_config.yaml line 15
Solution: Check indentation and quote strings with special characters

Missing Required Fields:

Error: Field 'cesiumLayers.base' is required
Solution: Add at least one base layer configuration

Invalid Values:

Error: cesiumViewer.homeButton must be boolean
Solution: Use true/false instead of strings

Advanced Configuration¶

Environment Variables¶

Support for environment variable substitution:

# Use environment variables for sensitive data
plugins:
  external_api:
    config:
      api_key: "${EXTERNAL_API_KEY}"
      endpoint: "${API_ENDPOINT:https://default.example.com}"

Configuration Inheritance¶

Support for configuration profiles:

# Base configuration
base: &base
  cesiumViewer:
    fullscreenButton: true

# Development profile
development:
  <<: *base
  cesiumViewer:
    baseLayerPicker: true

Dynamic Configuration Updates¶

API Endpoint for Runtime Updates:

@app.post("/api/config/reload")
async def reload_configuration():
    try:
        new_config = load_config(config_dir)
        app.state.config = new_config
        return {"status": "success"}
    except Exception as e:
        return {"status": "error", "message": str(e)}

Troubleshooting¶

Common Issues¶

Configuration not loading:

  • Check file paths and permissions

  • Verify YAML syntax with online validator

  • Check server startup logs for error messages

Changes not taking effect:

  • Restart backend server after configuration changes

  • Clear browser cache for frontend changes

  • Verify configuration API endpoint returns updated values

Validation failures:

  • Use schema validation tools to check structure

  • Compare with working configuration examples

  • Check for required fields and data types

Performance issues:

  • Large configurations may impact startup time

  • Consider splitting complex configurations

  • Use configuration caching for frequent access

Best Practices¶

Configuration Design¶

  • Keep it Simple: Use clear, descriptive names

  • Group Related Settings: Organize by functionality

  • Document Defaults: Specify default values clearly

  • Validate Early: Check configuration on startup

Security Considerations¶

  • Sensitive Data: Use environment variables for secrets

  • Access Control: Restrict configuration file permissions

  • Validation: Validate all configuration inputs

  • Logging: Avoid logging sensitive configuration values
